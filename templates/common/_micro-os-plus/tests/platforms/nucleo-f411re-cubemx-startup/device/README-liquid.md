## stm32cubemx

The content of this folder is generated by STM32CubeMX, for a CMake
Toolchain/IDE.

Note: be sure the button to generate `main()` is enabled, to benefit
from having the required hardware initialisations in a single place.

The configuration is stored in `stm32cubemx.ioc` and the content can
be updated at any time.

### Customisations

The code generated by STM32CubeMX provides a simple, but functional, startup
logic and a main function. To accommodate a more elaborate initialisation
logic and a main() function located in the application, some
customisations are required.

Fortunately, STM32CubeMX uses `USER CODE` sections, which are not
overwritten when regenerating code.

#### `Core/src/main.c`

There are two customisations done to main:

- rename `main()` as `cubemx_main()`, to avoid clashing with the
  µOS++ specific `main()`

```c
/* Private user code ---------------------------------------------------------*/
/* USER CODE BEGIN 0 */

// Renamed to cubemx_main() to avoid clashing with the µOS++ specific
// main(); called explicitly from
// micro_os_plus_startup_initialise_hardware_hook() (src/hooks.cpp),
// which expects it to return, not loop forever.
//
// Warning: the final `while (1)` loop below must stay commented out
// (with the `return 0;` in its place), otherwise this function never
// returns.
#define main cubemx_main
int cubemx_main (void);

/* USER CODE END 0 */
```

- comment out the infinite loop, so `cubemx_main()` returns instead of
  blocking forever, and add a `return 0;` in its place:

```c
  /* Infinite loop */
  /* USER CODE BEGIN WHILE */
  // while (1)
  //  {
      /* USER CODE END WHILE */

      /* USER CODE BEGIN 3 */
  //  }
  return 0;
  /* USER CODE END 3 */

```

`micro_os_plus_startup_initialise_hardware_hook()` (`src/hooks.cpp`)
simply calls `cubemx_main()`; the initialisation calls
(`HAL_Init()`, `SystemClock_Config()`, `MX_GPIO_Init()`, etc.) stay in
`main.c`, unchanged.

#### `src/wraps.c`

The two functions actually being wrapped:

- wrap `main()`
- wrap `__libc_init_array()`

To wrap the two functions, add the following to the linker options:

```txt
  -Wl,--wrap=main
  -Wl,--wrap=__libc_init_array
```

```c
// Trick to intercept the call from _start(), since we need to do a
// little bit more than STM32CubeMX initialization.
int __wrap_main(void)
{
  micro_os_plus_startup_run_main();

  while (1) {
    __WFI(); // Wait For Interrupt
  };
}

void __wrap___libc_init_array(void)
{
  // Silence this call, the static initializers will be called in the
  // µOS++ startup code.
}
```

#### `stm32f4xx_it.c`

The SysTick handler is not generated by STM32CubeMX and must be added
manually:

```c
/* USER CODE BEGIN 1 */

void SysTick_Handler(void)
{
  HAL_IncTick();
}

/* USER CODE END 1 */
```

## Semihosting

The STM32CubeMX code does not support semihosted applications and defines
all syscalls locally, most of them as empty functions.

To overcome this, the syscalls must be wrapped to redirect to a different
set of similar functions, implemented by the µOS++ semihosting package.

To do this, add the following to the linker options:

```txt
  -Wl,--wrap=initialise_monitor_handles
  #
  -Wl,--wrap=_close
  -Wl,--wrap=_execve
  -Wl,--wrap=_exit
  -Wl,--wrap=_fork
  -Wl,--wrap=_fstat
  -Wl,--wrap=_fstat
  -Wl,--wrap=_getpid
  -Wl,--wrap=_isatty
  -Wl,--wrap=_kill
  -Wl,--wrap=_link
  -Wl,--wrap=_lseek
  -Wl,--wrap=_open
  -Wl,--wrap=_read
  -Wl,--wrap=_stat
  -Wl,--wrap=_times
  -Wl,--wrap=_unlink
  -Wl,--wrap=_wait
  -Wl,--wrap=_write
```

To enable wrapping in the semihosting package, add the following to the
`micro-os-plus/semihosting-defines.h` header file:

```c
// Wrap semihosting syscall functions.
#if !defined(MICRO_OS_PLUS_SEMIHOSTING_SYSCALLS_WRAP_ENABLED)
#define MICRO_OS_PLUS_SEMIHOSTING_SYSCALLS_WRAP_ENABLED
#endif // defined(MICRO_OS_PLUS_SEMIHOSTING_SYSCALLS_WRAP_ENABLED)
```

## CMake

The definitions generated by STM32CubeMX are used in `device/CMakeLists.txt`,
but not directly; they require a relatively elaborate workaround to extract
the lists of properties and reuse them in a more appropriate set of
libraries, consistent with the rest of the µOS++ projects.
